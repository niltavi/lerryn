# Lerryn 0.9.0 发布说明

> 人工审查和目标环境验证已完成，结果写在第 6.3 节。只剩 B01 的 24 小时运行在进行中，结束后更新第 6.3 节并删除这段说明。

0.9.0 是 Lerryn 的首个企业试用版。功能范围是 PRD 的 P0：外部 Agent 通过 API、MCP 或 CLI 建立和维护自动化任务，Lerryn 负责隔离执行、定时触发、凭证、记录和通知，人在控制台里观察和授权。版本号为什么是 0.9.0 而不是 1.0.0，见[发布流程](../release.md)第 1 节。

## 2 包含的内容

**Agent 入口。**

- 公开 API `/api/v1`，契约版本 0.9.0。`discover` 返回服务端版本、契约版本、能力和运行时。
- MCP（Streamable HTTP，无状态），工具注册表由契约生成。基于 MCP Go SDK 1.8.0，协议版本 2024-11-05 至 2026-07-28。
- `lerryn` CLI：`login`、`discover`、`tasks`、`runs`、`mcp`、`skills`，以及覆盖全部操作的 `lerryn api <operationId>`。
- 四个 Agent Skill（`lerryn-automation`、`lerryn-credentials`、`lerryn-troubleshoot`、`lerryn-operate`），可以用 `lerryn skills install` 安装。

**任务与执行。**

- 任务以清单和文件提交，有版本、差异和乐观并发（`If-Match`）；激活前必须有成功的测试运行（可关闭）。
- 运行时：Python 3.12（uv）、Node 22、Shell（bash 5），依赖按锁文件安装并缓存。
- 加固的 Docker 容器：非 root、只读根文件系统、去掉全部 capabilities、`no-new-privileges`、进程数和内存上限、`/tmp` 不可执行；网络只有 `none` 和 `full`。
- 取消、超时、重启恢复，运行中断时清理遗留容器。
- 运行阶段、结果、产物和事件，日志分页、续读和 SSE 跟随，单次运行上限 20 万行或 100 MiB。

**触发与调度。** cron（带时区）、webhook（令牌鉴权，幂等键）、API 发起；同一任务不重叠；全局和单项目的排队上限、单项目并发上限；停机错过的计划记为错过。

**凭证。** 个人凭证，经一次性填写页填写，信封加密（本地主密钥文件），运行时注入并在日志、事件和结果中遮盖；提交的参数、清单和任务文件里出现已填写的凭证值时拒绝；撤销后新运行不能再使用。

**工具。** 项目级工具登记，包括脚本工具（只读挂载到 `/sbx/tools/<名称>`）；任务经 `sbx mcp call` 调用 MCP 工具，调用记为 `tool.call` 事件。

**账号与权限。** 内置账号和一个 OIDC 提供方；访问令牌（范围 `read`、`write`、`execute`）代表成员本人，不能生成新令牌，也不能修改账号（建账号、改管理员身份、停用、重置密码只接受登录会话）；项目的三种角色；手机扫码配对得到只读会话；登录、注册和配对码兑换按客户端地址限速，部署在反向代理后面时用 `server.trusted_proxies` 指定代理的网段；关键操作写审计日志，经 API 查询。

**控制台。** 嵌入在二进制里的 Web 控制台：概览、任务、运行详情和日志、凭证、工具、通知、访问令牌、手机配对，以及管理员的用户、runner、审计和注册设置。

**通知。** 运行失败时发 webhook，预置飞书和 Slack 格式，签名可校验，短时间内的多次失败合并；默认只发往公网地址。

**部署与运维。** 单机（all-in-one，SQLite）和标准拓扑（多个 server、PostgreSQL、S3 兼容存储、独立 runner）用同一个镜像；`lerryn backup`、`restore`、`export`、`import`、`migrate-db`；主密钥轮换；Prometheus 指标；`/healthz` 和 `/readyz`。详见 [deploy.md](../deploy.md)。

## 3 兼容范围

| 项目 | 范围 |
| --- | --- |
| 数据库 | SQLite（单机）；PostgreSQL 15 及以上（发布前在 15 和 17 上跑过全部存储测试） |

## 4 安装与升级

全新安装见 [deploy.md](../deploy.md) 第 2、3 节。

从 main 上的开发构建升级到 0.9.0，按 deploy.md 第 8 节：

1. 备份数据库，主密钥单独保管。
2. 停止全部 server。
3. 把 `LERRYN_VERSION` 改为 `0.9.0`，拉取镜像。
4. 启动 server，启动时自动执行迁移，等 `/readyz` 返回 200。
5. **最后逐台升级 runner。** 顺序必须是先 server 后 runner：新版 runner 上报的新事件旧版 server 不认识，会被拒绝。

回退需要同时恢复升级前的数据库备份，只换回旧镜像不够。

## 5 公网部署必做事项

控制台能从公网访问时，开放访问之前做完以下几步，详细命令见 [deploy.md](../deploy.md) 第 11 节：

1. **先有管理员。** 用 `auth.initial_admin.username` 和 `auth.initial_admin.password_file` 预先创建，或在开放访问前完成首次注册。开放注册默认开启，部署后到首次注册之间，任何能打开控制台的人都可以注册成为管理员。
2. **关闭开放注册。** 配置了单点登录时，在提供方把应用只分配给需要的人。
3. **告诉 server 反向代理在哪。** server 在反向代理后面时，把代理所在的网段填进 `server.trusted_proxies`。不填时所有用户共用代理的地址，几次失败的登录就会让所有人暂时无法用密码登录，审计里记的也是代理的地址。多节点参考部署已经填好。
4. **指标不对公网开放。** 用单独的 `metrics.listen` 只开放给监控网络，或者设置 `metrics.token_file`；反向代理不转发 `/metrics`。
5. **备份主密钥。** 和数据库备份分开保管。丢失后已保存的凭证全部无法解密。
6. 只用 HTTPS；runner 主机不开放入站端口；runner 注册令牌按 root 凭证保管，所有 runner 注册完后从 server 配置中去掉。

## 6 已知限制

### 6.1 设计上的边界

- **runner 主机权限高。** runner 能调用容器运行时，基本等于所在主机的 root。runner 主机需要专门管理，不和其他服务混部。
- **隔离面向企业内部。** 默认的容器加固适合企业内部成员提交的代码，不适合运行陌生人提交的代码，也不适合跨组织多租户。
- **任务之间的网络隔离依赖 dockerd。** `full` 网络的任务之间不能互访，靠的是 dockerd 管理的 iptables 规则；关闭了 dockerd 的 iptables 管理，或者在 OrbStack 这类桌面环境中（包括在 Mac mini 上部署时），这项隔离不生效，runner 启动时会告警。runner 启动时检查任务网络确实关闭了容器间通信，手工建的、开着互通的同名网络会被拒绝。`full` 网络下任务仍能访问宿主机网关和宿主机上发布的端口。
- **已注入的凭证收不回。** 撤销只影响新运行。已经合法拿到凭证的脚本可以变换或外传这个值，加密和脱敏都拦不住，所以修改代码的权限和使用凭证的授权要一起看。
- **工具调用记录依赖任务配合。** 只有经 `sbx mcp call` 发出的调用会被记录，任务绕过 `sbx` 直接发出的请求平台看不到；工具凭证会进入容器。
- **SQLite 不能多节点。** 要扩容先用 `lerryn migrate-db` 迁到 PostgreSQL。
- **日志写入压在数据库上。** 并发运行多、输出量大时会增加数据库负担。
- **移动端只能看。** 没有推送，也不能做任何操作。
- **MCP 没有服务端主动请求。** 无状态模式下不发 sampling、elicitation 请求和 `list_changed` 通知。

### 6.3 发布前的审查与验证

**人工审查。** 按[人工审查清单](../review-checklist.md)逐项对照代码完成，没有阻塞发布的问题。发现并修复的问题中，影响行为的有：

- runner 注册令牌不能再顶替正在工作的 runner：已有的 runner ID 只有在安静下来后才能重新换取凭证，否则返回 409 `runner_id_in_use`，runner 会自动重试。
- 阶段消息、结果摘要、工具调用的参数摘要和错误改为先脱敏再截断，凭证落在截断处时不再留下前半段。
- `adminCreateUser`、`adminUpdateUser`、`adminResetPassword` 改为只接受登录会话，管理员的访问令牌调用它们得到 403 `insufficient_scope`。用令牌调这三个接口的脚本要改成在控制台操作，或用 `lerryn admin` 命令在服务端主机上执行。
- 新增 `server.trusted_proxies`；密码哈希有并发上限，登录尝试先计数再校验；注册按地址每分钟限 5 次；PostgreSQL 上并发注册不会再产生两个管理员。
- 已打开的日志跟随和事件流在登出、令牌撤销、账号停用后立即结束。
- 修改或重置密码时一并作废未使用的配对码。

**目标环境验证。** 在一台原生 Linux 主机（Ubuntu 24.04，arm64，Docker Engine 29.9.2）上按[目标环境验证手册](../target-env-runbook.md)完成，逐项记录见[验收矩阵](../acceptance-matrix.md)第 6 节：

- 全部检查和集成测试通过，包括 PostgreSQL 15 和 17，以及要求任务隔离生效的执行器测试。
- 两种拓扑的控制面容量达标；参考部署上 50 个真实容器的并发运行全部完成，日志完整，开始执行最多延迟 1.5 秒（[capacity.md](../capacity.md) 第 3 节）。
- 原生 dockerd 上任务之间的网络隔离生效。
- rootless Docker 全部通过；Podman 不支持。
- 单点登录和 Dex 联调通过。

**还没有覆盖的。**

- **B01 的 24 小时运行**正在进行，2026年11月3日 09:26（UTC）开始。
- 单点登录只和 Dex 联调过，还没有和企业实际使用的提供方联调；"没有分配的账号被提供方拒绝"和 HTTPS 下的 `Secure` cookie 要在那时确认。
- 验证主机是和开发机共用硬件的虚拟机，性能偏乐观；userns-remap 没有验证；手机只测了 iOS 模拟器，配对时要在模拟器上点一次；PostgreSQL 的备份恢复（`pg_dump`）没有自动化测试。
