# Lerryn 容量测试

本文是实施规划中 S5 和 M6"两种拓扑的容量测试"的结果：目标、测法、一次实测的数字，以及测试中发现的问题。验收矩阵见 [acceptance-matrix.md](acceptance-matrix.md)，部署时的容量规划见 [deploy.md](deploy.md) 第 9 节。

## 1 测什么

PRD 第 8 节给了规模（单机 100 个任务定义、5 个并发轻任务；多节点 2 个服务副本、1000 个任务定义、50 个并发运行）和两条体验要求（首屏 3 秒内可用，新增日志通常 2 秒内可见）。S5 另要求 PostgreSQL 承载 50 个并发运行、每个每秒 500 行日志。没有给出领取速度、接口耗时这类数字，下面的目标是本文提议的。

| 指标 | 含义 | 提议的目标 | 依据 |
| --- | --- | --- | --- |
| 领取吞吐 | 一次排入大量运行，runner 领取并上报结束，每秒完成的运行数 | 不低于 20 次每秒 | 远高于 PRD 规模下的正常需求（50 个并发运行、每个运行数秒到数分钟），留出一次性补跑、批量重跑的余量 |
| 领取延迟 | runner 空闲时，从 `startRun` 到运行被领取 | p95 不超过 1 秒 | Agent 发起运行后应当马上看到准备中 |
| 日志写入 | 实际写入的行数每秒 | 不低于施加负载的 95% | S5：单机 5 × 500 行每秒，多节点 50 × 500 行每秒 |
| 日志可见 | 一行日志从 runner 发出到轮询的读者读到 | p95 不超过 2 秒 | PRD："新增日志通常在 2 秒内可见" |
| SSE 推送 | 一行日志从 runner 发出到 SSE 订阅者收到 | p95 不超过 2 秒，并且一行不少 | 同上；控制台和移动端用 SSE |
| 负载下的接口耗时 | 写日志期间，概览、运行列表、运行详情、日志尾部、任务列表的耗时 | 每个接口 p95 不超过 500 毫秒 | 首屏 3 秒内可用：首屏要调几个接口，再加上浏览器渲染 |

## 2 怎么测

测试在 `tests/capacity/`，带 build tag `capacity`，不在 `make check` 中运行：

```bash
go test -tags capacity -run TestCapacity -v -timeout 30m ./tests/capacity/
```

可选的环境变量写在包注释里：`LERRYN_CAPACITY_PROFILES` 只跑一种拓扑，`LERRYN_CAPACITY_SCALE` 按比例缩小规模，`LERRYN_CAPACITY_SECONDS` 调整日志阶段的时长（默认 20 秒），`LERRYN_CAPACITY_OUT` 指定结果目录（`results.json` 和 `results.md`）。

每种拓扑先从当前代码构建 `lerryn`，启动真实的 `lerryn server` 进程，然后依次：

1. **建任务定义。** 16 个并发客户端用 `applyTask` 建完全部任务。
2. **领取。** 先在 runner 空闲时逐条发起 50 个运行，测领取延迟；再一次发起一批运行（单机 300 个、多节点 1000 个），测从发起到全部结束的吞吐。
3. **日志阶段。** 单机 5 个、多节点 50 个运行同时以每秒 500 行写日志（每 200 毫秒一批），持续 20 秒。同时有：SSE 订阅者跟随这些运行（单机 20 个、多节点 100 个，分布在各 server 上）；5 个读者每 250 毫秒用 `readRunLogs` 轮询；单机 4 个、多节点 8 个客户端不间断地依次调用概览、运行列表、运行详情、日志尾部和任务列表。
4. **记录资源。** 每秒采样 server 进程的内存和 CPU，PostgreSQL 容器每 5 秒采样一次，结束时记录数据库大小。

运行由**合成 runner** 执行：它们走 HTTP runner 协议注册、领取、心跳、上报日志和结束，但不启动容器。所以这里的数字是 server 和数据库的，不含 Docker 启动容器、准备环境的时间；容器侧由执行器集成测试和验收测试覆盖。合成 runner 和真实 runner 一样，收到 5xx 会重试，重试次数计入结果。

两种拓扑：

| | 单机 | 多节点 |
| --- | --- | --- |
| server | 1 个，`GOMAXPROCS=2`，近似 PRD 的 2 vCPU 试用主机 | 2 个，不限制 CPU，客户端轮流连接 |
| 数据库 | SQLite（WAL） | PostgreSQL 17 容器，`max_connections=400` |
| 对象存储 | 本地目录 | 本地目录（两个 server 在同一台机器上共用） |
| runner | 1 个合成 runner × 5 个槽位 | 3 个合成 runner × 20 个槽位 |

## 3 实测结果

### 怎么看这些数字

- 两种拓扑在 PRD 的规模下都达到了提议的目标，余量很大。瓶颈不在控制面：真实部署里每个运行的容器启动和环境准备要几百毫秒到数秒，远慢于这里的领取速度。
- 多节点下 SSE 推送的 p95 在 850 毫秒左右，p50 只有 23 毫秒。日志写入发生在一个 server 上、订阅者连在另一个 server 上时，订阅者要等那一侧的下一次检查。离 2 秒还有余量，但 SSE 接口改为经事件总线唤醒后应当复测。
- 日志可见的数字包含读者 250 毫秒的轮询间隔。
- "排队等待"是一次排入大量运行时的等待，随批量大小增长，不是领取本身的延迟。

## 4 发现的问题

**PostgreSQL 连接池。** 第一次测多节点时，日志写入只有施加负载的 73%，517 次 runner 调用返回 503，SSE 订阅者少收了 2.5 万行。server 日志显示连接数据库时报 `connect: can't assign requested address`：`database/sql` 默认只保留 2 个空闲连接，50 个运行同时写日志时，几乎每个请求都新建一个连接、用完关掉，客户端主机的临时端口很快耗尽。生产环境里同样的模式会造成 PostgreSQL 连接风暴，连接数还可能超过 `max_connections`。

修复：`store.Open` 对 PostgreSQL 设置连接池上限，空闲连接保留同样多，空闲 5 分钟后关闭；上限默认 30，可用 `database.max_open_conns` 调整。两个 server 加维护命令仍低于 PostgreSQL 默认的 100 个连接。修复后同样的负载写入 24914 行每秒，没有一次 5xx，第 3 节的数字就是修复后的。

**客户端断开记为错误。** 客户端取消请求时（例如关闭页面），server 以 ERROR 级别记录 `api handler failed ... context canceled`。这不是服务端故障，量大时会淹没真正的错误。已修复：请求的 context 已取消、错误又正是这次取消时，HTTP 接口和 MCP 工具调用都改记 DEBUG（`api request abandoned by the client`、`mcp tool call abandoned by the client`）；客户端还在、或者错误是别的原因时仍记 ERROR。

**写响应时客户端已断开记为错误。** Linux 上的复测中，单机拓扑的 server 日志有两行 `api handler failed ... write: broken pipe`：客户端先关了连接，server 写响应时失败，而这时请求的 context 还没被取消，上面的判断没有认出来。已修复：写入因 `EPIPE` 或 `ECONNRESET` 失败的同样按客户端离开记 DEBUG（`logging.ClientGone`，`logging_test.go`）。

## 5 局限

- 合成 runner 不启动容器，测的是控制面。带真实容器的端到端开销见第 3 节的目标环境复测；那里的任务不安装依赖，依赖安装的开销由执行器集成测试覆盖，没有在 50 个并发的规模下测。
- 所有进程在一台机器上，没有网络延迟，PostgreSQL 也没有限制资源。单机拓扑用 `GOMAXPROCS=2` 近似 2 vCPU，但内存、磁盘都比 PRD 的试用主机好。目标环境复测用的 Linux 虚拟机和开发机共用硬件，企业部署到实际主机后，应按手册第 4 节再测一次，并按结果调整默认并发和保留策略（PRD 第 8 节）。
- 单次运行 10 万行日志的分段浏览和续读由 A13 的验收测试覆盖，不在这里重复。
- 对象存储用的是本地目录。S3 只影响日志归档和产物，日志热数据在数据库里，不影响这里的写入和读取路径。
